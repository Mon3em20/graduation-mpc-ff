## 6. Acceptance criteria (check 8)

Reference: float64 Python (`expected_python_reference.json`) and 100 fixed-point emulations with different rounding seeds (offline Python; summary in section 6).

| Quantity | Reference | Emulation spread (100 seeds) | Acceptance |
|---|---|---|---|
| Completion | — | — | all three parties exit 0, exactly three result lines, no `Fatal error`/`stream truncated`/exception, `total=100` on both evaluation lines |
| `epoch=1 train_loss` | 2.3048472 | max |dev| 2.7e-6 | within **8.6e-5**: [2.304762, 2.304933] |
| validation loss | 2.2957986 | max |dev| 1.3e-5 | within 8.6e-5: [2.295713, 2.295885] |
| test loss | 2.2888813 | max |dev| 9.7e-6 | within 8.6e-5: [2.288795, 2.288967] |
| validation correct | 15/100 | 15 in all 100 seeds | **exactly 15** |
| test correct | 19/100 | 19 in all 100 seeds | **exactly 19** |

Tolerance derivation: the emulation only models rounding noise (max 2.7e-6 train, 1.3e-5 validation). The only real-MPC accuracy datum is the batch-3 prototype audit (`docs/reports/secure_bp_matrix_numerical_audit.md`), whose largest per-sample loss error against FP64 was 8.568e-5 (it includes MP-SPDZ's exp/log/division approximations that the emulation lacks). The acceptance band is the larger of the two, 8.6e-5 ≈ 5.6 quanta of 2^-16. Count criteria: the smallest margin by which any evaluation sample's true label beats / loses to the best other logit is 1.99e-3 (validation) and 2.04e-3 (test); the largest emulated logit deviation is 2.1e-4, and the prototype's measured logit error was 2.8e-5, so counts can only change if logit errors exceed ~1e-3 (about 5x the emulation, 36x the measurement). Hence exact counts are required; a different count is a failure, not noise.

Abnormal behaviour (treat as failure, stop and keep logs): NaN/`inf`, a loss outside the band (a no-update or wrong-layout run is detectable: see section 7), `Fatal error`, "stream truncated" (a peer died), "Cannot read from input" / out-of-input errors, or no completion within 600 s. The timeout is derived from data: the smoke program has 91,096 VM rounds, so 600 s means > 6.6 ms per round, more than 100x the >= 49 µs per round lower bound implied by the scalar diagnostic that timed out at 12.2M rounds, and far above the 0.49 s the 1,095-round prototype needed in total. Unread input is not detected by MP-SPDZ; the exact token counts in section 4 are what guarantee consumption.

## 7. What the one-epoch smoke test can and cannot show (check 9)

It verifies on the real protocol: the programs compile and run under Rep3 Ring 64 with the real flags; runtime-owner `INPUTMIXEDREG` input in the sequential loop; matrix shapes 128, 8 and 100; per-party stream consumption; strict-positive ReLU, softmax/cross-entropy, deltas, gradients, the final batch of 8 and parameter persistence over three batches; gross numerical faults (this also bounds MP-SPDZ's approximation error at B=128 over three updates).

Discriminating power (offline, float64 on the smoke data): train / validation loss are 2.304847 / 2.295799 for the reference; **no updates** gives 2.305436 / 2.300938; **untransposed weights** 2.301486 / 2.291644 (and 14/21 correct); **learning rate x2** 2.304260 / 2.290992 — all outside the band, so these errors are detectable. A **+1.56 % learning-rate bias** gives 2.304838 / 2.295714 (9e-6 / 8.5e-5 shift) and is **not** detectable. Dividing the last batch by 128 instead of 8 is also invisible here because the loss is measured before the update.

It cannot verify: multi-epoch fixed-point drift (the emulation predicts max parameter drift of 6e-5 after 3 updates versus 1.8e-3..4.1e-3 after 200), accumulation of probabilistic-truncation noise, rare truncation failures over ~9e7 truncations, learning behaviour (the loss is still near ln 10), accuracy against the 76.6 % / 77.2 % baseline, runtime, memory and communication of the full run, or the sensitivity of epoch 2–5 losses. The full run's per-epoch losses (2.2747, 2.1616, 1.8416, 1.3058, 0.9092) are the next checks; stop if epoch 1 is not near 2.2747.
