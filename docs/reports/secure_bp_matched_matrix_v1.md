# SECURE-BP-MATCHED-v1 — batched-matrix implementation (pre-run report)

**Status: source-level and Python-numerically verified; MPC compile-only verified; MPC online execution NOT performed (reserved for the user).**

## 1. Why a second implementation

`bp_matched.mpc` (scalar loops) is mathematically correct but not executable in practice. Compile-only statistics from the pinned MP-SPDZ compiler (`compile.py -E ring -l -M`, which reproduces the exact statistics logged for the prototype run):

| Quantity | `bp_matched.mpc` (scalar) | `bp_matched_matrix.mpc` | Ratio |
|---|---:|---:|---:|
| Virtual-machine rounds | 19,965,875,172 | 5,638,872 | 3,540x fewer |
| Probabilistic truncations | 6,638,164,835 | 91,680,035 | 72x fewer |
| Bit triples (comparisons) | 1,761,310,000 | 933,945,000 | 1.9x fewer |
| Integer triples / simple mults (nominal) | 6.63e9 / 6.63e9 | matrix mults + 2.3e7 simple | — |
| Integer dot products (matrix products) | 0 | 37,185,200 | — |

Evidence for the bottleneck: the scalar 9-sample diagnostic (`bp_matched_diagnostic.mpc`) needs 12.2M rounds and did not finish within 600 s (`results/mpc/bp/diagnostic_fullarch_seed42_20261113/logs/time-P1.txt`, exit 124). That gives a *lower bound* of about 49 µs per round on this machine, i.e. at least 1.0e6 s (~11 days) for the scalar full run. The same bound puts the matrix program at >= 276 s of pure round latency; its true wall time (local matrix compute, bandwidth, 9.3e8 bit triples for comparisons) is **unmeasured** and must come from the user's run. The scalar cost is dominated by per-product truncation (6.6e9) and one VM round per scalar multiplication; the matrix program truncates once per matrix-product output and uses native Rep3 matrix multiplication (communication proportional to outputs, not multiplications). Comparisons (strict-positive ReLU masks, ~6.5e6 of them) and the per-row softmax/log remain per-element secure operations and are now the dominant cost.

Recommendation: use `bp_matched_matrix.mpc` for the final run. Keep `bp_matched.mpc` as the verified-but-infeasible reference implementation.

## 2. Implementation (new, isolated; scalar program untouched)

* `mpc/programs/bp/bp_matched_matrix.mpc` — full experiment (5 epochs, 39x128 + 8, 1000/1000 evaluation in chunks of 100).
* `mpc/programs/bp/bp_matched_matrix_smoke.mpc` — generated by `scripts/generate_matrix_bp_smoke.py`; only three constants differ (1 epoch, 2x128 + 8 training samples, 100 validation, 100 test).
* Same input-stream format as `bp_matched.mpc`, so the corrected bundle `~/secure-bp-runs/SECURE-BP-MATCHED-v1_seed42_corrected/` is used unchanged.

Per batch: load rows (sequential loop, owner `(start + sample) % 3`) -> `X.direct_mul(W)` + bias -> strict-positive ReLU mask `Z > 0` (kept and reused for the derivative) -> per-row stable softmax / cross-entropy -> `D3 = P - Y` -> `D2 = (D3 W3^T) * M2`, `D1 = (D2 W2^T) * M1` -> weight gradients `H^T D` accumulated unreduced and reduced once -> bias gradients as row sums -> SGD. Parameters persist across batches and epochs; the final batch of 8 uses its own buffers and divides by 8.

### Differences from the scalar program (all documented numerical effects, not semantic changes)

1. Dot products are accumulated exactly and truncated once per output element (scalar truncates every product).
2. SGD step is `(0.05 * grad) * (1/B)` with `1/B` an exactly representable `cfix` (1/128, 1/8). A single constant `0.05/128` is 25.6 quanta and would be stored as 26 (+1.56 % learning-rate bias). The Python fixed-point emulation shows this bias moves epoch-5 loss from 0.9092 to 0.8906 and accuracy from 766/772 to 773/776; the chosen form stays within about 1e-4 of float64 (regression test `test_single_constant_update_is_measurably_biased`). The matrix prototype used the single-constant form at B=3, where the error is only 0.03 %.
3. Evaluation predicts with `argmax(logits)` (as the plaintext baseline does) instead of `argmax(softmax)`.
4. ReLU is `Z * (Z > 0)` with the mask reused for the derivative (the scalar program compares twice).

Unchanged: architecture, seeds, splits, order, learning rate, `sfix(16,31)`, Rep3 Ring 64, truncation configuration (`compile-run.py -E ring` sets `use_trunc_pr` and `use_split(3)`; the program sets no options).

## 3. Verified facts

**Python numerical verification (offline, `scripts/verify/matrix_bp_reference.py`, `run_matrix_reference.py`, `tests/test_secure_bp_matrix_matched.py`):**

* The float64 simulator consumes party queues exactly as the MPC program does (owner formula, 9003/9001/8996 samples, all 27,000 consumed) and equals PyTorch float64 SGD over the baseline `DataLoader`: parameters after every epoch differ by <= 1.1e-16; epoch losses equal; validation 766/1000 and test 772/1000 correct.
* It reproduces the recorded float32 baseline (`results/baselines/bp.csv`, seed 42): epoch losses 2.27470, 2.16157, 1.84164, 1.30576, 0.90916; validation 76.6 %; test 77.2 %.
* The consumed training order equals the baseline DataLoader order in all five epochs.
* Fixed-point *emulation* (16 fractional bits, exact accumulation, probabilistic truncation, quantized constants; exp/log/division evaluated in float and rounded): after 200 updates the max parameter drift vs float64 is 1.8e-3 to 4.1e-3 (three rounding seeds), epoch-5 loss within 1e-4, validation 766-767, test 772. Raw output: `results/mpc/bp/matrix_matched_v1_preflight/python_reference_seed42.json`. This is an estimate of error accumulation, not proof of MP-SPDZ behaviour.

**Source level:** matrix dimensions/orientation (`[in,out]` weights, `direct_mul_trans` for hidden deltas, `direct_trans_mul` for gradients), strict-positive derivative, bias gradients, `/B` with B=8 for the final batch, persistence, owner and consumption order all checked (tests assert the program text).

**MPC compilation (compile-only, scratch copy of the pinned compiler; command in `results/mpc/bp/matrix_matched_v1_preflight/COMPILE_COMMAND.txt`):** `bp_matched_matrix.mpc` and the smoke profile compile without errors in ~15 s; statistics saved in the same directory. The compile warning "Probabilistic truncation leaks some information (eprint 2024/1127)" is expected and applies to the already-accepted truncation configuration. `-l` does not change the statistics.

**Runtime owner:** `input_from(regint)` compiles to `INPUTMIXEDREG` (run-time player numbers), confirmed in bytecode of a minimal program; the loop that reads inputs is a sequential `for_range`.

## 4. Remaining unverified assumptions / risks

1. **No MPC execution has been performed for either new program.** Run-time behaviour, wall time, memory and communication are unknown. Run the smoke profile first.
2. MP-SPDZ's approximations of `exp`, `log`, division and probabilistic truncation are not modelled in the Python emulation. The batch-3 prototype audit (max error 2.2e-4 against FP64) is the only MPC numerical evidence; it does not cover B=128, multiple batches or epochs.
3. Probabilistic truncation in the 64-bit ring can fail with probability growing with |value|/2^64; values here are small (raw magnitude well below 2^45), so failures are expected to be negligible over ~9e7 truncations, but this is an order-of-magnitude argument, not a proof. A failure would appear as a sudden loss spike.
4. The runtime message "The computation domain is too small for low-round truncation; it would need ... bits" is printed by the VM about the exact (non-probabilistic) truncation and is informational; it is a run-time notice, not a compile error and not a correctness failure. The "probabilistic truncation leaks information" line is a compile warning about the chosen protocol option.
5. Only the epoch-5 model is evaluated (like-for-like with the baseline for seed 42, whose best-validation epoch is 5).
6. The matrix variant is not bit-identical to the scalar variant; both are compared with FP64, not with each other.

## 6. Manual commands (NOT executed by the engineer)

> The smoke-run commands in this section are superseded by [secure_bp_matrix_smoke_preflight_audit.md](secure_bp_matrix_smoke_preflight_audit.md), which avoids overwriting `Player-Data/Input-P?-0` (it uses `-IF`).

Assumes `MP_SPDZ=$HOME/MP-SPDZ`, and inputs go in `Player-Data/Input-P{0,1,2}-0`.

```bash
# 0. Offline checks (safe)
cd ~/graduation-mpc-ff
.venv/bin/python -m unittest discover -s tests
.venv/bin/python scripts/verify/verify_secure_bp_inputs.py \
  ~/secure-bp-runs/SECURE-BP-MATCHED-v1_seed42_corrected

# 1. Back up Player-Data
cp -a ~/MP-SPDZ/Player-Data ~/secure-bp-runs/player-data-backup_$(date +%Y%m%d_%H%M%S)

# 2. Smoke profile (3 batches; compare with expected_python_reference.json in its bundle)
cp ~/secure-bp-runs/SECURE-BP-MATCHED-MATRIX-v1_smoke_seed42/Input-P?-0 ~/MP-SPDZ/Player-Data/
MP_SPDZ_ROOT=~/MP-SPDZ scripts/run_mpc.sh bp_matched_matrix_smoke.mpc \
  results/mpc/bp/matrix_matched_v1_smoke_seed42.log

# 3. Full run (only after the smoke profile agrees)
cp ~/secure-bp-runs/SECURE-BP-MATCHED-v1_seed42_corrected/Input-P?-0 ~/MP-SPDZ/Player-Data/
( cd ~/MP-SPDZ && /usr/bin/time -v python3 Scripts/compile-run.py -l -M -E ring bp_matched_matrix ) \
  2>&1 | tee ~/secure-bp-runs/SECURE-BP-MATCHED-v1_seed42_corrected/run_matrix.log
```

`scripts/run_mpc.sh bp_matched_matrix.mpc <log>` is an equivalent wrapper for step 3 (it copies the source into MP-SPDZ `Programs/Source`).

Expected during a healthy full run: five lines `epoch=k train_loss=...`. For seed 42 the Python reference gives 2.27470, 2.16157, 1.84164, 1.30576, 0.90916 (fixed-point noise ~1e-4); stop and investigate if epoch 1 is far from 2.2747 (e.g. near 2.30). Final lines: `validation loss=... correct=766 total=1000` (766-767 expected, loss ~0.788) and `test loss=... correct=772 total=1000` (~0.778).

Metrics to collect: wall time (`time -v`, VM per-thread timings printed by the party binaries), "Data sent" / "Global data sent" (MB) lines, VM rounds from the compile output, peak RSS, then the revealed losses/counts above. No model parameters are revealed by the program.
